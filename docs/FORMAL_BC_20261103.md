# Expanded BC round and L4 tuning

The 381-record run documented below predates the broader admission policy in
[BC_DATA_EXPANSION_20261103.md](BC_DATA_EXPANSION_20261103.md). New imports accept
all source modes/levels and supervise usable command windows without requiring
90% whole-game reconstruction coverage. The active dataset remains immutable.

The new formal pipeline is `scripts/run_formal_bc.py`. It runs tests, tunes kernels
and microbatch size, builds cloud-backed BC shards, and starts BC from the previous
119M BC weights with a fresh optimizer. The planned round is 8 epochs of 16,384
balanced WAIT/non-WAIT draws per epoch, 128-frame histories and learning rate 3e-5.
The run name is `119m_formal_bc_expanded_20261103`. PPO is a subsequent stage.

## Live launch evidence

The formal 119M BC job is running on L4, tracked at
[W&B qrr5pni8](https://wandb.ai/weidemingdeguge-test/cr-rl/runs/qrr5pni8).
The completed build contains 381 compatible replay records: 89 Cochon123 and

The builder exhausted the supplied source tables before its 512-record target;
it did not weaken compatibility filters. This is not the full upstream corpus.

After excluding 74 evaluation-deck records, the whole-match split assigns 245
records to training and 62 to validation. Training has 400,337 usable rows,
15,561 card-play labels and 119 ability labels; validation uses 1,024 sampled rows.
The dataset manifest hash is
`ee185072c41b9db39bc2ad77a90662a750241cc8b3deff9d723c9404e3bae919`.
No additional cross-source deduplication was performed, so replay counts are
record counts, and the split does not guarantee absence of duplicate source games.

The first 64 optimizer updates completed on the formal model. After initial
startup, the observed 1,536-sample blocks took approximately 36–38 seconds
(40–42 samples/s), below the short tuning probe as expected for different data.
Separate integration acceptance trained two tiny-model epochs from these shards,
restored optimizer state (4 to 8 updates), and loaded the BC weights into PPO.
That acceptance is an interface/recovery check, not a policy-strength evaluation.

## Measured tuning

L4, PyTorch 2.11.0+cu130, BF16, production model, real human-replay history windows.
Timing includes CPU window preparation, normalization, device transfer, forward,
backward, clipping and AdamW. Every case uses effective batch 96 so optimizer work
is comparable; one group warms up and two groups are measured. These are short
throughput probes, not model-quality comparisons.

| Microbatch | Entity padding | Optimizer | Samples/s | Peak allocated GiB |
|---:|---|---|---:|---:|
| 4 | Full 200 slots | AdamW | 13.79 | 6.17 |
| 4 | Actual entities, rounded to 16 | fused AdamW | 43.46 | 3.59 |
| **8** | **Actual entities, rounded to 16** | **fused AdamW** | **51.64** | **5.12** |
| 16 | Actual entities, rounded to 16 | fused AdamW | 50.14 | 8.15 |
| 24 | Actual entities, rounded to 16 | fused AdamW | 48.81 | 11.19 |
| 32 | Actual entities, rounded to 16 | fused AdamW | 44.68 | 14.24 |

Selected: microbatch 8, gradient accumulation 12, effective batch 96, BF16,
fused AdamW, automatic PyTorch SDPA backend selection. Compared with the measured
baseline, throughput improved about 3.74 times. The selected case also passed a
synthetic all-200-entities capacity stress test at 10.29 GiB allocated memory.
Actual formal throughput varies with history/entity counts and data I/O.

Forcing Flash Attention alone failed with the current attention masks. The formal
run therefore uses automatic SDPA selection; it does not claim a Flash-only path.
The optimization trims only masked entity padding before normalization/transfer.
No weights or action-space layout change. Tests compare policy/value outputs with
and without padding trimming. No custom Triton kernels were introduced.

## Data interface and storage

- IL_Replay: `VanguardX101/IL_Replay`, pinned revision
  `059d43a02138a34b1b3009cc2acc7630fb99a638`. Existing two source shards are reused
  from Drive; this round does not download the entire 252k-game corpus locally.
- Cochon123: `Cochon123/clash-royale-replays`, pinned revision
  `10cca44e9d863d06cf078f142d3e744f78698b0a`. The published cleaned legacy subset
  provides 1,592 candidate matches. `prepare_cochon_replays.py` adapts card plays
  and labelled ability activations into the same event interface as IL_Replay.
- Per user instruction, no additional cross-source deduplication is performed.
- `build_bc_shards.py` targets 512 reconstructed matches in bounded 16-match shards.
  Candidate counts are not training counts: simulator/table compatibility, action
  execution coverage and label validity determine the final usable rows.
- Source event tables do not contain complete original arena states. crforge
  reconstructs observations. Cochon legacy levels are unknown, and unspecified
  evolution forms use base form; these assumptions are retained in provenance.
  The result is approximate state-conditioned BC supervision.
- Training keeps the existing legal-action masks and whole-match validation split,
  and excludes configured evaluation deck combinations. Validation samples are
  balanced across WAIT/card plays with a reserved allowance for available abilities.

## Monitoring and recovery

The supervisor publishes `status.json` and log snapshots to Drive every 20 seconds.
Data manifests advance after each verified shard. BC checkpoints are published and
verified after each epoch, with optimizer/RNG state for continuation. W&B records
BC losses, gradient norms and validation metrics; its link is in `bc.wandb.json`.
The actual training command is saved in `training_config.json`.

For a new Colab after interruption, restore/download compressed dataset shards and
the epoch checkpoint, then run `train_bc.py --resume CHECKPOINT` with the saved
training configuration. The BC dataset hash must still match. This restores at an
epoch boundary; it does not resume a partially completed epoch. The supervisor has
a three-hour budget and monitors actual work; runtime availability is not guaranteed.
