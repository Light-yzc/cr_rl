# BC 本地验证与后续方案（2026-11-10）

## 结论

本地完成五组、每组64步的真实checkpoint对照；没有一组的最终控制集综合目标优于原checkpoint的初始6.6202。当前证据不支持通过立刻换GTrXL、增大模型、或加入实体动作query来解决平台期。类别编码修正有进一步试验价值，但尚未证明能提高泛化或加速收敛。超长时长直接截断在本次迁移中出现明显梯度尖峰，不应原样推入生产。

这轮确认了两件不同的事：模型可以降低固定小集训练目标，主干和动作头没有整体断梯度；现有梯度累积的条件分母有组成依赖，能够用精确计数修正。它们都不等于已经验证出实战更强的模型。

## 实验协议与范围

- 本地RTX4090；已有F盘conda Python3.10/Torch2.6.0+cu124，没有安装环境或启动云端GPU。
- 所有新增实验文件、数据、临时文件与缓存位于G盘。单GPU trainer顺序执行，不并发训练。
- 共同父模型：prior020 epoch5/step1300，122621959参数；SHA256为a196b85348f4fe6b64ffc8451dccd3656123860afd0278074ebb520cd9bcc3e1。使用epoch5基线有意保留已评测父模型；本次不是epoch7续训结果。
- 64训练状态、64原验证对局状态，每组32个choice-WAIT＋32个普通出牌，均保留128帧同座历史。控制集不参与反向传播。没有技能标签，不代表技能分支已被验证。
- 每microbatch固定2WAIT＋2play，micro4×accum16=64；同seed20261110、fresh AdamW、LR1e-5/tile3e-5、timing prior0.20、sigma1、clip1、64步。不是生产optimizer恢复。
- FP16 autocast，FP32参数、帧编码器、落点头与概率边界；动作query新分支也为FP32。本次没有证明纯FP16稳定。
- 128个选中完整history＋time/legal masks中没有精确重复/冲突；未审计全数据集的标签冲突。
- 五组用了同一控制集，因此它现在是开发集；只有32个控制出牌，准确率每变化一例就是3.125个百分点。没有新增实战，不能据此汇报胜率提升。

### 各变体如何解释

1. 类别组：queue/enemy_play_cast从数值通道清除后用共享card embedding＋有序投影，ability_unit转为存在标志；新增786432参数。这同时改变了旧输入和新增通路，step0已经不同，不是保持旧策略的迁移。其最终控制优于原版64步，但仍差于原checkpoint初始，不能称已加速泛化。
2. 时长组：将适配后的三列buff_ms截至36，即360000ms。选中history最大原始buff为999999ms，没有覆盖真正1e9近永久时长；影响14/64训练history和7/64控制history。其负结果不能否定真正极端时长应做语义编码，但已否定本次直接截断可无代价迁移的假设。
3. 组合组：最终控制比自身初始略低，但仍未优于原checkpoint；中途有很大梯度尖峰。一次小幅变化不足以推广。
4. 动作query组：7个query用历史context及手牌身份查询当前实体，零初始化输出残差，新增495361参数。真实122M模型上128条完整history的初始最大logp/value误差均为0.0/0.0。这证明新增分支能保留初始输出；终局结果没有证明收敛收益。若后续出现收益，还需匹配参数量的MLP消融才能归因于实体attention。

## 数值、内存与速度边界

- 五组均退出0、loss及unscale后梯度有限、GradScaler保持32。有限不等于优化平稳；时长组/组合组仍有数千梯度尖峰与强裁剪。
- 日志采样RSS峰值不超过2370MiB，CUDA allocated峰值不超过4913MiB。这是64状态诊断，不是完整BC训练内存承诺。
- checkpoint用mmap读取并在meta上构建模型后逐tensor入GPU，不载入生产optimizer、不复制整个CPU模型。每组结束清除解压映射缓存，不保存五份模型/优化器。
- 各组墙钟受系统内存、缓存、频率影响，未交错重复，不能把某组更快归因于结构加速。未作新的吞吐倍数承诺。

## 已验证的累积分母问题

另做16个人工logits CPU案例，覆盖不等出牌数、零出牌microbatch、尾批、技能标签、prior0.2/平衡时机与sigma0/1。现有micro均值累积与整有效batch目标相比，案例最大梯度相对L2误差为49.66%；使用整有效batch计数后，最大梯度绝对误差为2.38e-07。这是数值算术检验，不是实战或收敛实验，也不是生产批次误差的估计。

当前prior0.2路径每microbatch应贡献：

`sum(weighted timing NLL)/N + sum(conditional action NLL)/N_act + position_coef*sum(tile NLL)/N_play`

其中N/N_act/N_play由整个有效batch预先统计，各micro贡献相加，不再额外除accumulation。无先验平衡时机路径使用整个有效batch的WAIT/ACT计数及类别存在数。技能计入ACT但不计入PLAY，零类别分母与尾批必须显式处理。本次五组固定2WAIT2play，所以现有写法本就等价，五组对照不受该问题影响。

## 建议采用的后续方案

1. **保留122M主干和原checkpoint，先修正有效batch归一化。** 这是本轮有明确数值依据的工程修正。迁移时记录计数、旧新目标/梯度对照，独立分支试训，不与输入重编码或新动作头一起上。它保证目标不随microbatch组成改变，不保证自动提升胜率。
2. **用更广的数据检验一次有限续训，而非再背同64状态。** 沿用175训练局、原对局级验证划分及既有验证协议，最多先跑1个epoch；不以本次64控制状态调参。分别看choice时机、条件选牌、硬落点及soft excess KL，保留阶段最新checkpoint并回收更早中间文件。若同协议验证无改善，不机械延长长训。
3. **并行审计监督保真度。** 将修复强度、原动作与实际执行的时间/手牌/落点偏差分层，优先确认高置信度动作；法术时机不可简单扩成大时间窗口，普通WAIT也不可全部当成同强度负例。当前只有11248个独立出牌＋504技能训练标签，大量相邻帧不能算成独立战术示范。数据瓶颈是待检验假设，不宣布已证明。
4. **输入改进只保留版本化候选。** queue/enemy_play_cast确属类别字段，值得修；下一候选应保留旧通路，以零初始化残差/分阶段训练迁移，超长buff按普通时长/近永久/未知语义分别设计。不可把本轮直接清零、截断后的结果当成已通过的生产方案。
5. **速度优化接在目标校正之后。** 先固定有效batch96再比较micro4/8/16，核对梯度及FP16有限性后测吞吐；设备侧累计指标、集中主机读取也可独立profile。未经测量不承诺加速倍数。
6. **晋升须用未调参验证与固定换边实战。** 训练loss下降或开发小集变好均不充分；遵守既定评测预算。当前不推荐换GTrXL/Mamba、扩300M或部署本轮诊断权重。
