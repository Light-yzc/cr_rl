# 客户端状态读取与出牌桥接方案

记录日期：2026-11-04，Asia/Shanghai。用户确认优先研究 `Jason-XII/cr-memory-reader` 作为状态来源，并要求记录出牌接入方案。

本页记录源码调研结果与待实施设计。尚未安装或运行这些外部项目，未在本机验证客户端兼容性、读取完整性或出牌延迟；文档准备不改变当前 PPO 训练任务的优先级。

## 1. 接入路线

建议首先验证以下闭环：

```text
Android / 模拟器
  → 内存读取器（实体、HP、圣水、时钟、手牌）
  → 观测适配器与新鲜度检查
  → 与训练一致的 4 Hz、128 帧历史
  → 当前冻结 Actor：WAIT / 手牌槽位与落点 / 技能
  → 动作调度与坐标映射
  → ADB 触控
  → 内存动作事件、手牌轮换等执行确认
```

状态读取和触控执行可以独立实现。第一版用 ADB 模拟点击，不需要为了出牌写游戏内存，也不要求用视觉模型识别战场。初始化时仍需校准屏幕布局，不能把游戏地图坐标直接当成屏幕像素。

### 读取器的文档与运行入口存在差异

[技术指南](https://github.com/Jason-XII/cr-memory-reader/blob/main/x86_64/内存读取技术指南.md) 描述 JSON API / SSE 和 `/api/v1/state` 等端点，但本次核查的实际 [x86_64 采集入口](https://github.com/Jason-XII/cr-memory-reader/blob/main/x86_64/tools/capture_native_entity_stream.py) 是 native helper、Python 状态合并、JSONL 日志及 Pygame UI，默认包名为 `nullsroyale.rel.free`。未在该入口看到 HTTP/SSE 服务实现，不能把文档端点直接写成已经可调用的依赖。

实际接入前要确认运行分支、构建与输出契约，再决定直接消费数据流还是在本项目增加本地状态服务。法术效果、目标坐标、觉醒语义等仍有未标定项；指南中不同阶段的 profile 与默认 Nulls 运行路径不能混作同一次验收。

## 3. 第一版出牌：ADB 触控

Actor 的普通出牌动作解码为 `(hand_slot, tile_x, tile_y)`。适配层将手牌槽转换为屏幕手牌中心，将地图格子中心转换为屏幕落点，然后执行“点击手牌 → 点击落点”。常驻 ADB shell 可减少反复建立进程/连接的开销，已有实现见 [clash-jev 的设备层](https://github.com/bytelabs-oss/clash-jev/blob/main/clash_jev/device.py)。

需要独立处理：

- **坐标标定**：记录设备 serial、分辨率、方向、手牌区域和竞技场映射；手牌与竞技场可能采用不同缩放，不能只套一个全屏比例。地图视角需按逻辑座位转换，不能用红/蓝颜色猜 seat。
- **动作身份**：决策保留手牌槽和当时 card ID；发送前检查槽位仍是该牌、当前状态足够新鲜且仍在同一场对局。过期动作丢弃并重新决策，不无限排队。
- **等待与技能**：WAIT 不发送触控。技能单独映射按钮并检查可用性；尚未实现的技能动作必须明确拒绝，不能当成普通卡牌点击。
- **待确认动作**：第一版最多保留一个 in-flight 出牌，避免手牌尚未轮换时连点同槽。确认或超时后才解除；确认超时和异常需进入日志。
- **执行结果**：记录 `requested → sent → confirmed / rejected / timed_out`。ADB 返回成功只代表触控命令执行，不能当成成功出牌。

### 出牌确认

优先关联读取器提供的动作序号、玩家、card ID 和执行事件，再用预期手牌轮换、圣水变化及场上结果交叉核对。单独的圣水下降不是充分证明；实体出现也不能覆盖法术、技能等所有动作。

为每次动作保存本地 action ID、对局 ID、观测 tick、槽位、card ID、地图/屏幕坐标、发送时间、确认时间及证据类型。执行回执不足时保持 `unconfirmed`，不补造成功或精确落点。

端到端记录状态年龄、推理耗时、触控耗时和确认耗时，并报告 P50/P95；现阶段没有本机实测值，不承诺满足 250 ms 的决策节拍。

## 4. 备选：RoyaleBot 的 socket 动作接口

[link.py](https://github.com/RoyaleGym/RoyaleBot/blob/main/royalebot/link.py) 定义经 ADB 端口转发连接的 socket 协议：4 字节小端消息长度加 MessagePack 消息；`send_play(play_id, hand_slot, x, y, tick)` 发送出牌请求，并接收 `play_result` 事件。握手需声明对应协议与 `can_play`。

这是准备过的 Nulls 客户端内的游戏链路，不是普通 ADB 自带服务，也不是 `cr-memory-reader` 默认输出。使用前必须独立验证客户端版本与准备工具。其 [bridge.py](https://github.com/RoyaleGym/RoyaleBot/blob/main/royalebot/bridge.py) 当前跳过技能按钮；其坐标单位、卡牌目录、模型保存格式及观测构造不能直接套到本项目。

第一阶段建议保持读取器加 ADB 的组合，socket 路线作为后续对照，不同时维护两套未验收的执行后端。

## 5. 与现有训练接口对齐

现有模型使用 crforge 的结构化观测及合法动作 mask。客户端读取器输出不是同一 schema，需要逐字段记录“直接读取、推导、未知”，至少核对：

- 对局生命周期、时钟单位、采样间隔、逻辑 seat 和坐标方向。
- 卡牌 data ID 到训练词表的映射、手牌槽位、下一张牌和已知卡组；未知牌保持 unknown。
- 实体身份及生命周期、阵营、位置、HP/max HP、兵种/建筑类型；缺失状态、buff、flags 等不能伪装成已验证数值。
- 费用、部署区域、待执行状态、技能冷却等合法性依据；依据不足时不能声称与模拟器 mask 完全一致。
- 历史窗口按训练决策节拍组织，不把读取器的每条高频事件直接当作一帧。记录缺帧/陈旧状态，并明确对应策略；跨局清空历史。

若读取器暴露模拟器策略训练时不可见的信息（例如对手隐藏手牌、未公开部署），观测适配器仍须遵守原有可见性约束，不直接扩展 Actor 输入。

## 6. 待实施与验收

- [ ] 锁定读取器源码 revision、设备/客户端包、ABI、版本与库指纹；确认支持范围。
- [ ] 只读采集一场完整对局，核对实体、塔血、手牌轮换、圣水、时间与对局边界；保留字段缺口表。
- [ ] 编写观测适配器，验证与训练的 ID、单位、坐标、历史及可见性规则一致。
- [ ] dry-run 输出模型建议和落点覆盖图，不发送触控；检查缺失字段、状态年龄与推理延迟。
- [ ] 标定手牌与地图坐标，单独验证少量手动指定出牌和技能，不先接无限自动循环。
- [ ] 接入受限次数的模型动作，验证去重、过期丢弃、出牌确认、超时和停止逻辑。
- [ ] 导出与视频对齐的观测/决策/执行日志，报告拒绝率、确认率、坐标误差与延迟，再决定是否进入闭环模型评估。
