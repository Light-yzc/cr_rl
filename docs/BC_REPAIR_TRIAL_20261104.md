# BC 局部修订与 L4 对照（2026-11-04）

## 诊断核实

本轮从实际校验的 step4096 checkpoint 及冻结 Stage 2 数据出发，保留原始文件。
当前只保留会话 `bc-repair-l4`（L4）；先前的 CPU 会话已经关闭。

用户提出的四项诊断中：

1. **学习率漏传不是当前根因。** `train_bc.py` 会继承 checkpoint 的 `tile_learning_rate`，v2 没有保存值时也默认 `3e-4`。实际 Stage 2 配置已经是主干 `3e-5`、落点头 `3e-4`。`run_all_bc.py` 现在显式传参，便于检查，不能把这项清晰化说成修好了此前低学习率训练。
2. **单分片集中排序真实存在。** 它可能引起局部偏移，但尚未证明每32步的全部震荡均由它造成。新增工作集窗口混洗，在缓存预算下混合多个分片。默认保留 window=1 以兼容旧运行；新实验申请64，按最大分片解压尺寸及128 GiB预算保守缩小。
3. **分组均值会丢失卡牌身份的组内对应。** 新增 hand、pending、ability、enemy-play 的按槽位拼接投影；deck 和 enemy-seen 继续做集合汇聚。全局数值字段保留原顺序，使身份可与槽位上的坐标、费用和时间组合。实体及其他记录仍能提供部分信息，不能断言旧模型完全看不到进攻方向。
4. **平衡 timing 与自然先验失配是真实风险。** 平衡损失改变目标先验，不会强迫每个状态都输出50%动作。新增自然先验的 importance-weighted timing，条件选牌/落点仍使用动作密集采样。目标先验来自训练分区；抽样先验来自完整 epoch，避免每微批次重新估计导致的噪声。WAIT邻域原有排除规则不变，未把相邻帧直接改为出牌标签。

Query 位置分量的初始尺度确实比部分共享分量小，但“50倍淹没”和“LayerNorm锁死上限”不是已证实的定量结论；当前已经有FP32落点头及query残差。可学习空间读出是待验证的改进，而不是确定的根因修复。

PPO 可以从随机策略学习，并非只能精炼。当前先做BC修订是成本和实验顺序的选择。独立critic不把负优势直接反传进actor；actor使用固定、脱离计算图的优势做策略梯度。联合动作的信用分配存在困难，但不必然导致WAIT坍缩。不能把这类推测写成数学必然。

## 代码修改

- `ModelConfig.readout_version`：旧checkpoint默认1；只有显式升级的新分支为2。普通resume不改变布局。
- 实体空间基增加可学习线性映射，初始化为`0.02 * I`，保持旧贡献。
- Tile空间分量单独归一化，加context-conditioned FiLM；残差门初始化为0，逐步学习启用量。迁移时原解码路径保留，避免直接重置训练好的主干。
- 有固定记录语义的卡牌组增加零初始化有序残差投影；迁移初始不改变已有汇聚输出。
- 显式迁移只允许新增已知参数。所有原模型tensor保留，原optimizer动量按名字迁移，新参数使用新状态。缺失旧参数、未知键或不兼容模型会报错。
- 迁移输出一致性测试使用FP32及明确浮点容差；BF16下新增线性映射会改变舍入路径，不承诺逐bit一致。原模型tensor逐项保持不变，不等于所有精度/硬件下的输出逐bit不变。
- `--shard-mix-window`、`--timing-objective`、`--upgrade-readouts`和`--max-updates`均写入新运行记录。中途resume拒绝改变采样和timing语义；修改实验使用新目录与显式初始化。
- 训练日志增加timing、条件选牌、落点损失、梯度范数、实际学习率和空间门值。

新增测试覆盖：工作集边界/覆盖/复现，自然timing的正确先验最优点与条件选牌梯度保留，旧模型输出与optimizer迁移，新增空间和有序分支梯度，以及记录身份置换可区分。当前本地 **118 tests passed in 4.21s**，Ruff通过；L4 Linux在新增最后一项梯度测试前重跑 **117 passed in 5.96s**。本地真实小回放数据还完成了自然timing训练两步、中途恢复再两步，以及从冻结父checkpoint显式读出升级后的两步优化（step4→6，新optimizer状态101项，原版90项）。

读出分支新增1,442,817参数，总量由121,179,142变为 **122,621,959**；实体/时间Transformer的层数与宽度不变。初始远端验收曾因缺少锁定版本的`crforge_env` Python wrapper失败；已安装精确commit后重跑通过，原失败状态归档，没有在失败验收下启动训练。BC本身不调用JVM；本次未声称在新L4上完成模拟器机制或对战验收。

## 实际执行协议

入口：`scripts/run_bc_repair_trial.py`。它在同一L4上顺序执行，不启动第二训练实例。

| 项目 | 固定条件 |
|---|---|
| 父模型 | 已校验step4096，SHA `d1945756c448849f0d8736cc02bdb35542b029cfe85690ddf905016c5d1675b7` |
| 数据 | Stage 2原冻结manifest，SHA `e7edb3151eb064450335fd807533db8025be16f9d73f7ee8f7f82d43b82ca732` |
| 分区 | 原split registry及留出卡组，seed 20261102 |
| 长度/batch | 128帧，microbatch16，accumulation6 |
| LR | 主干3e-5，落点3e-4，两组均相同 |
| 修订组 | 有序/空间读出升级，多分片混洗，自然先验timing |
| 原版组 | 旧读出，单分片排序，平衡timing |
| 步数 | 每组新增1000步；修订组先跑，两组都从4096初始化 |
| 监测/备份 | 每32步固定快速验证，每128步及结束保存并校验Drive checkpoint |

同一冻结集和seed保持验证抽样一致，但不是精确延续原epoch的剩余样本：两组均显式从父模型/动量开始新epoch采样。此对照改变了多项因素，只回答整组修改是否有帮助，不能分别归因；如有改善，再做拆分消融。较旧GPU缓存和后跑组的预热优势也使端到端时间不宜直接比较。

目标是观察同一集合的条件选牌、落点NLL/within2/L1、动作窗口响应、自然动作概率及波动。`within2>35%`、`L1<7`、`slot>45%`只是用户提出的目标，尚无依据作为通用的战术可靠性标准。初期指标、单个快速验证点或平均动作概率接近先验均不能证明对战变强。

不承诺15–20分钟完成：需要恢复979个分片和验证历史缓存，训练预计时间以实测速率为准。控制器不会自动晋级、覆盖父权重、启动PPO或宣称强度提升。两组完成后还须完整验证和新的留出换边评估。
